# 통합 설계 결정 기록

소스는 `frontend/`와 `backend/`로 분리하고 각 서비스에 Dockerfile과 Railway 설정을 둔다. 폴더·파일별 역할은 [프로젝트 구조 설명서](PROJECT_STRUCTURE.md)를 참고한다.

## 브랜치 통합

- `origin/main`: 회원, 학습방, WebSocket 기능을 제공했지만 SQLite와 별도 모델 계층을 사용했다.
- `origin/AITraining`: `main`보다 한 커밋 앞서며 고1 수학 JSON, Chroma 인덱서, 검색 CLI를 추가했다.
- `origin/front`: 별도 Git 이력의 React/Vite 정적 UI였다.
- `local-mysql-snapshot`: 통합 전 로컬 MySQL 스키마와 문서를 보존한다.
- `origin/main`: 백엔드, AITraining 자료 처리, 프런트, MySQL 통합 코드의 현재 기준이다.

## 핵심 결정

1. 운영 데이터 저장소를 MySQL 하나로 통일했다.
2. 대형 임베딩 모델은 기본 의존성에서 제외했다.
3. AITraining JSON을 앱 시작 시 MySQL 문서/청크로 멱등 인덱싱한다.
4. 생성형 응답 제공자는 OpenAI 하나로 통일하고, API 키 누락이나 장애 시 규칙 기반 튜터로 폴백한다.
5. OpenAI Responses API에는 최근 학생·AI 메시지를 역할별로 유지해 전달하고, 선택한 단원의 RAG 근거와 현재 하브루타 단계를 함께 제공한다.
6. 프런트는 JWT를 저장하고 모든 주요 화면에서 실제 REST API를 사용한다.
7. 테스트는 SQLite로 빠르게 격리하고 실제 MySQL은 별도 스모크 테스트로 확인한다.
8. 운영 그룹 채팅은 JWT와 학습방 권한을 확인하고 MySQL에 영속화한다.
9. Railway의 여러 백엔드 인스턴스 사이 WebSocket 이벤트는 Redis Pub/Sub으로 전달한다.

## 데이터 흐름

1. 사용자가 가입하고 JWT를 발급받는다.
2. 학습방을 만들거나 초대 코드로 참여한다.
3. 실제 RAG 카탈로그에서 학교급·학년·단원을 선택해 학습 세션을 시작한다.
4. RAG 서비스가 과목·학교급·학년·단원 코드로 해당 범위의 2022 연계 청크만 찾고, 의미 유사도와 어휘 일치도를 혼합해 재정렬한다.
5. 최근 10개 대화를 역할별로 구성하고, 의미 있는 학생 설명만 하브루타 단계 진행에 반영해 개념·근거·명료성·참여도 루브릭을 계산한다.
6. 관련 근거와 후속 질문을 AI 메시지로 저장하고 실제 검색기·생성 제공자·출처를 프런트에 반환한다.
7. 종료 시 학습 기록과 정리노트를 생성한다.
8. 같은 RAG 자료로 복습 퀴즈를 생성하고 시도를 기록한다.

## 알려진 경계

- 4영역 설명 루브릭은 교육적으로 검증된 성취도 점수가 아니라 프로젝트 내부의 설명 품질 지표다.
- OpenAI API 키가 없거나 호출에 실패하면 규칙 기반 응답으로 자동 폴백한다.
- `몰라`, `힌트` 같은 도움 요청은 오답 점수나 단계 진행으로 처리하지 않고 직전 질문을 더 작은 질문으로 나눈다.
- 진행 중인 세션은 MySQL 메시지에서 복원하며 브라우저 새로고침 후에도 이어갈 수 있다.
- 사용자별 분당·일일 AI 요청 한도와 출력 토큰 상한으로 공개 테스트 중 비용 급증을 막는다.
- API는 Chroma 의미 검색을 우선 사용하고 사용할 수 없으면 가벼운 어휘 관련도 검색으로 전환한다. 두 검색 모두 `RAG_CURRICULUM_YEAR=2022` 정렬 정책과 선택 단원 코드 필터를 공유한다.
- Redis가 없으면 WebSocket 채팅은 단일 백엔드 인스턴스 안에서만 브로드캐스트된다.
- Railway 배포는 관리형 MySQL·Redis, 공개 Backend·Frontend 네 서비스 구성을 전제로 한다.
